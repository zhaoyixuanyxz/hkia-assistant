# 技术架构安排

## 推荐技术栈
### 前端
- **Next.js**：负责产品 UI、路由、报告页面、知识库和市场情报入口。
- **Tailwind CSS + shadcn/ui**：实现深色金融 Agent UI、表单、卡片、弹窗、侧边栏等组件。
- **Recharts 或 ECharts**：MVP 使用少量基础图表；后续扩展到 12+ 专业保险/金融图表。

### 后端
- **FastAPI**：提供对话、报告、认证、知识库、市场情报 API。
- **DeepSeek OpenAI-compatible API**：MVP 主模型。
- **SQLite 或本地 JSON 存储**：MVP 可用的轻量持久化方案。推荐 SQLite，因为后续迁移 PostgreSQL 更顺畅。
- **PostgreSQL**：阶段 2 起作为正式业务数据库和 LangGraph Checkpointer 后端。
- **Qdrant**：阶段 2 起用于长期记忆和知识库向量检索。
- **LangGraph**：阶段 2 起用于多 Agent 状态机编排。

### 运维与观测
- **本地 `.env`**：管理 DeepSeek、后端端口、CORS、PostgreSQL、Qdrant 等配置。
- **LangSmith 可选**：阶段 2 起用于 Prompt 和 Agent trace。
- **Docker Compose**：阶段 3 起统一启动前端、后端、PostgreSQL、Qdrant。

## 模块边界
### Frontend App
负责用户可见体验：
- 登录页。
- 会话列表页。
- 对话页。
- 画像侧边栏。
- 报告页。
- 知识库页面骨架。
- 市场情报页面骨架。

前端不直接调用模型，不直接拼装保险建议。所有 AI 和业务编排通过后端 API 完成。

### Backend API
负责业务能力边界：
- `auth`：MVP 登录和用户身份。
- `chat`：消息收发、会话状态、Agent 回复。
- `profile`：用户画像提取、摘要、快照。
- `report`：报告生成、报告读取。
- `knowledge`：知识库示例数据、搜索接口骨架。
- `market`：市场情报示例数据、更新接口骨架。
- `compliance`：免责声明注入、输出风险检查。

### Agent Orchestration
阶段 1 使用简化编排：
- 单个 InsuranceExpert 风格 Prompt。
- 每轮对话后做轻量画像摘要。
- 报告生成时使用报告专用 Prompt，并可读取少量示例产品数据生成「产品类别建议」。

阶段 2 升级为 LangGraph：
- `InsuranceExpertAgent` 主导对话。
- `ProfileArchitectAgent` 每 3-5 轮更新画像。
- `ReportArchitectAgent` 决定报告叙事、产品类别和图表。
- `VisualizerAgent` 生成图表配置。
- `KnowledgeRetrieverAgent` 在知识库可用后加入检索，负责把用户画像和报告目标转成产品检索查询。

## 核心数据流
### 阶段 1 MVP 数据流
1. 用户登录，创建或进入会话。
2. 前端发送用户消息到后端。
3. 后端读取会话历史和当前画像摘要。
4. 后端调用 DeepSeek 生成顾问式回复。
5. 后端保存消息，并更新轻量画像摘要。
6. 用户点击生成报告。
7. 后端根据消息历史、画像摘要、示例产品和示例市场信息生成报告。
8. 前端展示叙事报告、基础图表和免责声明。

### 阶段 2 多 Agent 数据流
1. 用户消息进入 LangGraph 状态机。
2. InsuranceExpertAgent 判断当前对话目标。
3. ProfileArchitectAgent 定期更新结构化画像和记忆。
4. KnowledgeRetrieverAgent 根据需要检索产品知识，返回候选产品、匹配理由和来源链接。
5. ReportArchitectAgent 基于用户画像、候选产品和合规规则生成报告结构。
6. VisualizerAgent 生成图表配置。
7. PostgreSQL 保存状态，Qdrant 保存向量记忆和知识库向量。

### 阶段 3 数据流
1. 管理员导入或触发更新产品/市场数据。
2. 后端解析、标准化、校验来源链接。
3. 结构化数据写入 PostgreSQL。
4. 文本内容生成 embedding 写入 Qdrant。
5. Agent 在对话和报告生成时进行检索增强。
6. 具体产品推荐必须引用检索命中的产品记录；若检索不足，只能给出产品类别建议。

## RAG 检索增强产品推荐架构
RAG 是阶段 2/3 的功能进阶，用于把「动态用户画像」和「真实产品知识库」连接起来。它不是简单搜索产品名，而是根据用户的人生阶段、家庭结构、财务目标、保障缺口、风险偏好和价值观，检索最相关的产品候选，再由报告 Agent 做组合、解释和合规表达。

推荐链路如下：

1. `ProfileArchitectAgent` 输出当前用户画像摘要、关键实体和配置目标。
2. `ReportArchitectAgent` 提出本次报告需要覆盖的产品类别，例如医疗、重疾、储蓄、寿险、年金。
3. `KnowledgeRetrieverAgent` 生成结构化检索请求，包含画像标签、产品类别、约束条件和排除项。
4. 后端同时执行全文搜索和向量语义搜索。
5. 检索层返回候选产品、匹配分数、命中字段、来源链接和更新时间。
6. `ReportArchitectAgent` 只能从候选产品中选择具体产品，并说明匹配理由、适用假设和风险提示。
7. 报告保存所引用的产品 ID，方便前端展示来源和后续审计。

阶段 1 可保留 RAG 接口形状，但只返回示例产品；阶段 2 建立 Qdrant 和检索编排；阶段 3 接入真实产品数据后，RAG 成为具体产品推荐的强制路径。

## 数据模型建议
### MVP 最小模型
- `User`：用户 ID、邮箱或用户名、密码哈希、创建时间。
- `Conversation`：会话 ID、用户 ID、标题、状态、创建时间、更新时间。
- `Message`：消息 ID、会话 ID、角色、内容、创建时间。
- `ProfileSnapshot`：画像 ID、用户 ID、会话 ID、摘要文本、结构化字段 JSON、更新时间。
- `Report`：报告 ID、会话 ID、标题、正文 JSON、图表 JSON、免责声明、创建时间。
- `ProductStub`：产品 ID、名称、类别、摘要、官网链接、来源说明。
- `MarketIndicatorStub`：指标 ID、名称、数值、解释、来源链接、更新时间。

### 后续扩展模型
- `MemoryEntry`：长期记忆、实体记忆、偏好、重要程度、embedding ID。
- `Product`：正式保险产品结构化数据。
- `ProductSource`：来源页面、抓取时间、审核状态。
- `ProductEmbedding`：产品向量索引记录、embedding 模型、索引状态、更新时间。
- `ProductRecommendationTrace`：报告引用了哪些产品、检索查询、匹配分数、选择理由。
- `MarketIndicator`：正式市场指标。
- `DataUpdateJob`：数据更新任务记录。

## 关键架构选择
### 为什么 MVP 不先上完整 LangGraph
完整 LangGraph 会提升长期可扩展性，但第一阶段最大风险是产品闭环是否成立。MVP 先用简单编排验证用户体验，后续再把业务边界迁移到 LangGraph 节点。

### 为什么 MVP 推荐 SQLite
SQLite 足够支撑本地开发和 Demo，又能保留关系型数据建模习惯。阶段 2 迁移 PostgreSQL 时，表结构和业务模型可以最大程度复用。

### 为什么知识库和市场情报先做骨架
真实数据导入和爬虫会带来大量清洗、审核、来源追踪工作。阶段 1 只需要证明报告生成可以消费这些数据，阶段 3 再投入真实数据管道。
