Vibe Code完整过程（技术）（AI编程规划路线）

设计一个…产品（App或者小程序）



1.产品需求设计一个产品文档（PRD）满足上述的想法需求，输出一份结构化的文档（markdown文件）

需要包含

a.产品定位（核心概念、产品哲学、专业术语表包含对象和类）

b.核心功能列表

c.用户流程（用户故事）

d.验收标准





2.技术栈需求

这个项目我想做成（）的产品，项目目标是不需要商用；（是否）考虑用户数据安全、性能优化和未来拓展性，请推荐合适的技术栈技术选型API接口设计数据模型设计错误策略处理





3.选技术栈的核心原则：

选主流的；遇到问题容易找到解决方案选成熟的；工具链完善，坑少选合适的：匹配项目规模。



架构设计需求技术栈确定以后，为我设计一个项目的完整结构方案包含：项目目录结构核心模块划分代码规范建议GIT版本管理我的项目目标是（可部署，需要一定扩展性）

特别提醒：好的架构应该是“刚刚好的”，满足当前需求，有一定拓展空间，但不会为了可能永远用不到的功能增加复杂度。（架构非一成不变，可随项目发展进行逐步调整）



4.项目管理需求

结合产品需求文档和技术架构，建构一套从基础架构、数据模型、状态管理、UI组件的可迭代交付、分模块跑通的全流程开发线。



5.总结问题需求正式启动任务操作之前将先前上下文总结出的内容进行整理并创建文件：

README.md（项目简介：项目是干嘛的）

（如何运行：怎么跑起来项目）

（技术栈：用了什么技术）





ARCHITECTURE.md

（技术栈及其选择原因）

（项目目录结构）

（核心模块说明）

（数据模型设计）

（代码规范）



6.自动化测试+一键启动项

（1）启动plan模式进行全栈自动化开发并自主完成所有执行操作（不需要经过我的同意，直接开启run everything模式）

（2）开发完成以后自动执行测试任务：观察（依赖环境是否安装、路径PATH是否添加进去、代码运行是否有问题出现bug的情况），出现无法运行的情况进行自我修复，测试不行继续检测并进入循环，超过循环五次以上也无法修复的问题给出详细的操作指南说明辅助开发人员进行手动操作。

（3）再完成开发+测试以后创建一个启动项可以自动跳过繁琐的终端执行命令等步骤，一次性跳转到用户界面进行体验，方便开发人员调研用户使用感受。





7.版本迭代（Git）+代码托管（GitHub）

目的：备份代码、回退版本、多人协作、为部署和CI做准备。不是“部署成功”，仓库本身不会让外人打开你的网站。



本地先有.git，再推远程：

git add . → git commit -m "说明" → git remote add origin（仓库HTTPS地址）→ git push



私密项目选Private；.gitignore务必排除密钥和运行时数据。

例子：.env（API密钥）、本地数据库/上传目录、node_modules/、虚拟环境目录 不进库。



GitHub上README是“门面”：别人clone或你自己回看时一眼懂项目干嘛、怎么跑；可在本地写好README.md再push，别只在网页点Add README（避免和本地不同步）。



打标签做基线（可选）：git tag v1.0-baseline，大改坏了能对照回退（可另写docs/版本回退说明.md）。





8.测试与验收（迭代过程中反复做）

分两层，别混为一谈：



（1）自动化测试（给开发用）

后端：cd backend && python -m pytest tests/ -q

一键检查脚本（若有）：scripts/run-checks.ps1（装依赖+pytest+前端build）

前端：cd frontend && npm run build（TypeScript+打包是否过）



（2）手工烟测（给产品/业务用）

按PRD验收标准走主流程；单独写「用户操作指南」（大白话：先完成核心动作A→再去模块B查结果→需要对比时用功能C）。

技术验收文档可单独放：docs/验收说明.md（接口列表+烟测步骤）。



（3）排障手册（DEV_RUNBOOK.md）

写清：运行环境版本、.env怎么配、端口占用、长连接被代理掐断、项目路径变更后依赖要重装等。

AI修不动时让人按手册操作，避免反复口头解释。



测试环境注意：自动化测试用临时数据，不覆盖本机真实库；声称“修好了”前要真跑过命令看输出（证据先于结论）。





9.部署上线（先搞清楚“托管”有几种）



【概念】

· GitHub托管 = 托管源码（备份/协作）

· 应用上线 = 某台机器24小时跑服务，用户浏览器访问网址

· Coze部署 = 单个Agent的API地址（stream_run），和完整Web项目（前端+后端+数据库+文件）不是一类东西



【本机开发态】

一键启动脚本（如 start.bat）：前后端分离则同时起API和前端开发服务；单体项目则起唯一入口。

环境：按技术栈装好运行时（如Node/Python）；.env里填第三方API密钥等敏感配置。



---



方案A：你电脑托管 + Tailscale（试点最快，但你关机别人用不了）



适合：先给2～3个同事试用，不想买服务器。

你要做：

① 装Tailscale（你和同事都要装，同一Tailnet；管理后台Invite user发邀请链接）

② 用「共享模式」启动（服务要能被局域网/虚拟网访问，不能仅限「仅本机可打开」的开发地址）

③ 把「内网访问地址」发给同事（Tailscale 里看你这台设备的虚拟 IP，再加项目用的服务端口，拼成浏览器能打开的链接）

同事：装Tailscale→登录→浏览器打开链接→看产品内帮助/操作说明

密钥：只在你本机.env，同事不用自己申请API。

缺点：你电脑得常开；数据在你本机数据库/文件目录里。



---



方案B：便宜云主机 + Docker（推荐长期；你关机同事也能用）



适合：小团队稳定用、最低成本24小时在线。

成本（2026参考）：

· 腾讯云轻量2核2G：约45～50元/月，活动有时99元/年

  介绍页 https://cloud.tencent.com/product/lighthouse

  购买 https://console.cloud.tencent.com/lighthouse/instance/create

· 阿里云轻量：类似

  介绍 https://www.aliyun.com/product/swas

  购买 https://swas.console.aliyun.com/#/servers/create

另加：第三方API（大模型/短信等）按量计费（和本机同一Key即可）



购买怎么选：Linux 镜像（如 Ubuntu 22.04）；2核2GB；地域选近的；云防火墙放行「对外提供网页」的端口。



服务器上4步（仓库里备好Dockerfile+docker-compose.yml）：

装docker → git clone私有库 → 复制.env.example为生产用.env并填API密钥 → docker compose up -d --build

同事只打开：云服务器对外的访问地址（控制台里的公网 IP 或以后绑的域名；不用 Tailscale、不用装开发环境）



本机历史数据想迁上去：scp打包上传（可选），写在docs/部署指南.md里。



更新流程：本机改代码→git push→SSH上服务器git pull && docker compose up -d --build。



---



部署方案怎么选（一张表）



| 需求 | 选 |

| 只自己开发 | 本机一键启动脚本 |

| 同事试用、你可常开电脑 | 方案A Tailscale + 共享模式启动 |

| 你关机也要用、同事零安装 | 方案B 云主机Docker |

| 只备份代码 | GitHub Private |



MCP（Cursor里GitHub/Cloudflare/Neon等）：帮你开发管仓库查文档；终端用户用不到，不能代替买服务器或docker compose。



公网部署安全提醒：方案B知道网址的人都能进；后期可加 HTTPS + 登录。API 密钥只在服务器生产环境变量/文件，勿提交 Git。





10.复盘清单（一个功能模块做完可勾一遍）



□ PRD/用户故事/验收标准是否更新

□ 主流程手工走通（对照用户操作指南）

□ pytest + npm run build 通过

□ README / DEV_RUNBOOK / 验收文档是否同步

□ .gitignore是否挡住.env和data

□ 需要交付他人时：选定方案A或B，写清“管理员做什么、用户打开什么链接”

□ push GitHub；若上云：防火墙端口已放行、生产环境配置、服务在跑且外网能打开





（全流程串联记忆）

PRD → 技术栈/架构 → 分模块开发 → 测试+一键启动 → Git/GitHub备份 → 选部署方案（试点A / 正式B）→ 发链接+用户操作指南 → 迭代时pull/build/烟测再来一轮
